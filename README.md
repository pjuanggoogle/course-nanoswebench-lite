# Nano SWE Bench Lite

Nano SWE Bench Lite is for educational purposes only.

Self-contained Python bug-fixing benchmark (`103` training tasks + `10` unseen
test tasks) designed for training and evaluating a **124M-parameter NanoGPT**
tool-calling coding agent.

These tasks were all distilled from public, open source benchmarks.  They
simulate issues found in SWE Bench Lite but reduced to fit in a minuscule
context window.

The micro benchmarks in this suite contain no Google proprietary code.

## Why These Task Constraints Were Needed for NanoGPT

Standard SWE-bench Lite tasks run against full checkouts of large open-source
repositories (such as `django/django`, `sympy/sympy`, or `pytest-dev/pytest`),
where individual source files are often thousands of lines long. A
124M-parameter GPT-2 model (`NanoGPT`) has a **1,024-token context window**
(`block_size = 1024`), and our harness defines a **512-token per-turn generation
limit** (`max_tokens = 512`) so a single assistant response never consumes more
than half the context window—which means a raw SWE-bench Lite repository file
cannot fit into the model's context window.

To make real SWE-bench Lite bugs solvable and learnable within NanoGPT's
1,024-token window, every task in `mytest/` is constructed under four
constraints:

1.  **Compact Source Files (≤ 1,800 Characters / 2–37 Lines)**:
    -   Each task extracts the buggy function or class from an upstream open-source
        issue into a small, self-contained Python module (`62–1,168` bytes, `2–37` lines).
    -   Because the `read_file` tool returns up to `1,800` characters per call,
        keeping every source file under `1,800` characters guarantees that a
        single `read_file` call shows the entire file at once.
    -   Without this constraint, a 1,024-token student would have to scroll
        through files in chunks using `start_line` and `end_line`—a behavior
        that large-context teacher models (`gemini-3.1-flash-lite`) never
        demonstrate because their context windows hold whole files at once.
2.  **Prompt + Observations Fit Within the 1,024-Token Window**:
    -   Both the source module and its `pytest` test file (`pass_to_pass` and
        `fail_to_pass` tests) are kept compact so that the problem statement,
        the `read_file` outputs, and the `pytest` failure traceback fit inside
        the `1,024`-token context window alongside the model's generated tool call.
3.  **Localized Bug Fixes (≤ 512 Tokens per Edit, Defined by Our Harness)**:
    -   We enforce a `512`-token single-turn generation cap (`max_tokens = 512`)
        in the harness and SFT dataset builder. Each task targets a focused
        1–10 line bug fix so that a clean `edit_file` call (`filepath`,
        `old_string`, `new_string`) fits within that 512-token generation limit
        instead of requiring a full-file rewrite.
4.  **Zero External Dependencies Beyond `pytest`**:
    -   All 113 tasks are distilled pure-Python snippets using only the Python
        standard library plus `pytest`, so each sandbox test run completes in
        under `0.3s` without Docker containers or third-party package builds.

## Task Splits (`103 TRAIN_TASKS` / `10 TEST_TASKS` / `5 DEV_TASKS`)

> **Warning — Split Imbalance Note:** The `TRAIN`/`TEST` splits defined here are
> defined badly. `TEST` relies heavily on the `astropy` (`4/10` tasks) and
> `seaborn` (`4/10` tasks) packages, which were not present in the original
> `TRAIN` split (and have only 2 tasks each in the expanded `103`-task `TRAIN`
> set). Recommend rebalancing the split across domains.

| Split             | Task Count | Purpose                                                                                                                                                                         |
| :---------------- | :--------: | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **`TRAIN_TASKS`** | `103`      | Teacher trajectory collection and SFT training                                                                                                                                  |
| **`TEST_TASKS`**  | `10`       | Strictly held-out evaluation (`0` training trajectories); never used for SFT                                                                                                    |
| **`DEV_TASKS`**   | `5`        | Fast in-domain sanity check subset of `TRAIN_TASKS` (`requests_query_params`, `pytest_repr_exception_handler`, `sympy_symbolic_polynomial_gcd`, `http_chunked_transfer_decoder`, `rate_limiter_token_bucket`) |
